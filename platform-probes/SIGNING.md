# Signing and trust for a Cosmopolitan fat executable (Windows, macOS, Linux)

Everything marked MEASURED was run in GitHub Actions (workflow `platform-signing`, final run 41063145930; earlier runs 41059710849, 41060017179, 41061298032, 41062288396 gave the same results for the parts they contained; workflow `platform-signing-upstream`, runs 41061301920 and 41062128825). Test certificates are throwaway (root CA, publisher leaf, time-stamp authority, all generated in the job). A purchased certificate and an Apple account are not available here; section 6 lists exactly what that blocks.

Test files: `app.c` (prints the OS/architecture slice it runs as and reads `/zip/asset.txt` from its own embedded zip), `dl_probe.c` (loads a system library at run time), `hello.c`, `jit_probe.c`; all built with cosmocc 4.0.2.

## 1. Windows: Authenticode on the Cosmopolitan file

### Why the file as built cannot be signed (MEASURED, recap)
The PE header inside the file has `NumberOfRvaAndSizes = 2` (optional header 128 bytes) and the section table is followed directly by a Mach-O header, so there is no room for data directory 4 (the certificate table). `Set-AuthenticodeSignature` says "not a valid Win32 application", `signtool` 0x800700C1, `osslsigncode` a PKCS7 decoding error (reproduced again in the final run).

### What works (MEASURED)
`pe_prepare_for_signing.py` copies the PE header to unused zero padding at file offset 0x1000 (inside `SizeOfHeaders` = 0x11000), with 16 data directories and a 240-byte optional header, and points `e_lfanew` at it. The old header and the Mach-O header stay where they were. The prepared file is then an ordinary signable PE.

All of the following were signed with a root that is trusted in the runner's `LocalMachine\Root` store, on **windows-latest (Server 2025, x64) and windows-11-arm (Windows 11 ARM64)**:

| signer / layout | Get-AuthenticodeSignature | `signtool verify /pa` | runs on Windows | hash unchanged by a run, still Valid |
|---|---|---|---|---|
| osslsigncode 2.8 (Linux), certificate appended | Valid | exit 0 | yes | yes |
| osslsigncode + RFC 3161 time stamp from a local TSA | Valid, timestamper = the test TSA | exit 0, "The signature is timestamped" | yes | yes |
| Set-AuthenticodeSignature (Windows PowerShell) | Valid | exit 0 | yes | yes |
| signtool sign /fd SHA256 | Valid | exit 0 | yes | yes |
| osslsigncode, then signtool `/as` (second signature, SHA384) | Valid | exit 0 | yes | yes |
| "zip slot" layout (section 1.2) signed by osslsigncode, with and without time stamp | Valid | exit 0 | yes | yes |
| "zip slot" layout signed by signtool | Valid | exit 0 | yes | yes |

The same signed files were also run, and their signatures re-verified with `osslsigncode verify -CAfile`, on **Linux x64, Linux arm64, macOS 26 arm64 and macOS 15 x86-64**: `sh ./file` and `./file` both work, the embedded zip asset resolves, the file hash is unchanged by the runs and the signature still verifies (also for the files signed on Windows by signtool and PowerShell).

Facts to keep in mind:
- Windows on ARM runs this file through **x64 emulation** (the program prints "Windows x86-64" on the ARM64 runner). The PE is x86-64 only; Cosmopolitan 4.0.2 has no native Windows-arm64 slice. Signing is identical.
- Adding a file to the zip after signing (`zip -A file.exe late.txt`, negative control) destroys the signature (`Get-AuthenticodeSignature`: NotSigned, `signtool`: "File not valid"); the file still runs. Rule: add every asset first, prepare the header, sign last, never touch the file afterwards (Microsoft's SmartScreen page says the same: do not modify signed files).
- Time stamping: the RFC 3161 token from a local `openssl ts` authority (HTTP, `application/timestamp-query`) was accepted by osslsigncode and by Windows' verifier (signtool prints the time and "Timestamp Verified by ... Test Timestamp Authority"). The certificate table then grows from 3,032 to 7,248 bytes; this matters for the zip (next section). `signtool /tr` was not run against the local authority (the TSA was a Linux-side process); that is a Microsoft client talking to a standard RFC 3161 server and is not expected to differ, but it was not measured.
- In the first run the second `-ts` signing (the zip-slot variant) failed once; its output was not captured, and it did not recur in the five later runs. Cause not identified; a signing script should retry a time-stamp server anyway.

### 1.2 The embedded zip and the certificate table (MEASURED)
Cosmopolitan appends its zip (the `/zip/...` read-only file system) at the end of the file, with the end-of-central-directory record (EOCD) as the last bytes. A signer appends the certificate table after that. Two layouts were tested:

- **Plain** (certificate appended after the EOCD): Info-ZIP `unzip -l` (exit 0), `zipinfo`, Python `zipfile` (asset read), .NET `ZipFile.OpenRead` on Windows, and Cosmopolitan's own `/zip` reader (the program prints the asset) all work on the signed file, with a 1.5 KB to 7 KB certificate table. Nothing needs fixing for these readers. A strict reader that insists on `EOCD + 22 + comment length == file size` would reject it; none of the tested readers do.
- **Zip slot** (`ape_zip_slot.py`): `reserve` pads the file to 8 bytes and sets the EOCD comment length to cover pad + 16 KiB that are not in the file yet; the signer then appends its certificate table exactly there; `fill` rewrites the WIN_CERTIFICATE length to the full 16 KiB and zero-fills. Result: the EOCD is still the last record and its comment ends at the end of the file, so even strict readers work. The EOCD comment length is part of the signed bytes (it was set before signing); the certificate table, the PE checksum and the directory entry are excluded from the Authenticode hash, so the signature stays valid. Windows (`Get-AuthenticodeSignature`, `signtool verify /pa`) accepts a certificate table with 13 KB of trailing zero padding, for osslsigncode and for signtool signatures, with and without time stamp. Cost: 16 KiB per file. Use it if any consumer of the zip is strict; otherwise the plain layout is simpler.

### 1.3 Upstream: what makes this the default (MEASURED)
`ape/ape.S` in Cosmopolitan 4.0.2 emits `.long 2 // NumberOfDirectoryEntries` followed by the export and import directory entries. Changing that to 16 entries (`.long 16` and `.fill 14,8,0` after the import directory; `ape_pe_optsz` is computed by the linker script from the section-table position, so SizeOfOptionalHeader becomes 240 by itself) is the whole change. Built from the 4.0.2 sources (`make o//ape/ape.o ...`) and linked into a test program in a copy of the cosmocc tree:
- `NumberOfRvaAndSizes = 16`, `SizeOfOptionalHeader = 240`, section table moved by 0x70 bytes, apelink accepted it;
- **no preparation step**: osslsigncode signs it (verification ok), signtool signs it and `Get-AuthenticodeSignature` says Valid on Windows x64; both the unsigned and the signed file run on Linux x64/arm64, macOS arm64/x86-64, Windows x64 and Windows arm64 (emulated).
Caveat: the `ape.o` rebuilt from the unmodified 4.0.2 sources was 24 bytes larger than the one shipped in the cosmocc zip (23,664 vs 23,640 bytes; `ape.lds` byte-identical), so the build recipe used here (the repository's own makefile) is not bit-for-bit the release recipe; the patched object was nevertheless fully functional on all five targets. Only the x86-64 half (which carries the PE and the x86 Mach-O header) was rebuilt; the arm64 half is the released one.
Suggested upstream change: the one in `ape/ape.S` above, plus (optional) an `apelink` flag or default that reserves a certificate slot as in 1.2.

## 2. Windows: Defender, SmartScreen, Smart App Control, WDAC

### Defender (MEASURED)
On both runners the settings were applied with `Set-MpPreference` and read back: `MAPSReporting` Advanced (2), `SubmitSamplesConsent` SendAllSamples (3), `CloudBlockLevel` High (2) and then ZeroTolerance (6), `CloudExtendedTimeout` 50, `PUAProtection` Enabled (1), real-time/behaviour/IOAV monitoring enabled. State: the ARM64 runner has real-time protection and tamper protection on by default and the cloud (MAPS) connection check succeeds. The x64 runner (Server 2025) has real-time protection off by default; it switched on within 25 s of the setting and the MAPS connection check failed (0x80508015) on the first try and succeeded on the second, after the setting had taken effect. (In the first runs of the day, before the retry was added, the x64 cloud check had failed; the verdicts below are from runs where it succeeded.)

Each of the 8 files (hello, app with zip asset, library-loading `dl`, prepared-unsigned, and the signed hello/app/app-with-timestamp/dl) was scanned with `MpCmdRun -Scan -ScanType 3` twice (cloud High, then ZeroTolerance) and **executed** under both levels: 16 scans "found no threats" and 16 executions exit 0 on each runner. The control (the standard antivirus test string) was detected both times as `Virus:DOS/EICAR_Test_File`, so the scanner was working. Signed and unsigned files got the same verdicts.

What this does and does not show: Defender's engine and its cloud lookup have no complaint about a plain Cosmopolitan program, a zip-carrying one, a library-loading one, or the signed versions, at the strictest cloud block level, on a connected machine. It does not show what a first-seen file with no history does on a user's machine in the field (runner images share a baseline; sample submission can only be judged by Microsoft's later verdicts, which this job cannot observe; `Get-MpThreatDetection` stayed empty).

### SmartScreen: NOT testable in CI
SmartScreen's application reputation is evaluated by Explorer/ShellExecute for files with the Mark of the Web (Zone.Identifier ADS) against Microsoft's cloud, per file hash and per signing identity. A CI job has no interactive shell launch and no download origin, and a throw-away root cannot be a reputable publisher. MEASURED only: a copy with `ZoneId=3` started from a process (CreateProcess, as the runners do) runs without any gate, signed or not. From Microsoft's documentation (Learn pages "SmartScreen reputation" and "Code signing options", fetched 2026-10-30): reputation is evaluated per file hash and per publisher certificate; a new signed binary can still warn until hash or publisher accumulate reputation (no fixed threshold; "several weeks and hundreds of clean installs from a wide audience"); EV no longer gives an instant bypass (removed 2024); unsigned and self-signed files get the strong "Windows protected your PC" prompt; the Microsoft Store (MSIX) avoids it; there is no mechanism to submit a file for consumer SmartScreen review (enterprise administrators can use the Microsoft Security Intelligence file submission portal). What can be inferred: signing is necessary (unsigned/self-signed are treated alike), and not sufficient on day one. What cannot be inferred: how long a new publisher takes, whether the cloud has anything on this specific file.

### Smart App Control / WDAC (MEASURED where possible)
- Smart App Control: state registry value `VerifiedAndReputablePolicyState` = 0 (off) on the ARM64 Windows 11 runner, not present on Server 2025. So SAC enforcement cannot be exercised. Microsoft's page says SAC blocks unsigned files without positive reputation and checks all executables, so a signed file matters there.
- WDAC (App Control for Business) in **audit mode** (`CiTool --update-policy`, AllowMicrosoft base + a publisher rule built from the signed test file, option 3 audit): on both runners the unsigned Cosmopolitan file produced event 3076 ("would have been blocked"; validated signing level 2), the file signed with the allowed test publisher produced **no** 3076, and `whoami.exe` (Microsoft-signed control) produced none. Event 3089 for the signed file shows the code-integrity engine parsed the signature of the prepared file: SignatureType 1, PublisherName "Test Software Publisher", IssuerName "Test Root CA (CI only)", the Authenticode SHA-256, validated signing level 4. So WDAC treats the prepared, signed file as an ordinary signed PE. (Audit only: nothing was enforced, to keep the runner usable.)

## 3. macOS

### Findings (MEASURED, macOS 26.6 arm64 runner; macOS 15 x86-64 for the run tests)
1. **The bare file cannot be signed in a way that travels.** `codesign -s -` on the fat file works but reports `Format=generic` (the file does not start with a Mach-O header, `otool`/`lipo` say "not an object file"), leaves the file bytes unchanged and stores the signature in extended attributes (`com.apple.cs.CodeDirectory`, `.CodeRequirements`, `.CodeSignature`). `codesign --verify --strict` passes and the file runs. After `cp -X`, zip+unzip (i.e. any download or archive) the signature is gone ("code object is not signed at all"). The file has no arm64 Mach-O header at its start (`lipo -info`: "can't figure out the architecture type"), so there is no Mach-O to carry a signature. Not notarizable as a bare file (notarization takes .app/.pkg/.dmg).
2. **What actually runs on Apple Silicon is a loader compiled on the user's machine.** The shell stub in the file (`MZqFpD=...`) looks for `ape` in PATH or `${TMPDIR:-$HOME}/.ape-1.10`; if absent it decompresses embedded C source (`ape-m1.c`) and builds it with `cc`, printing "please run: xcode-select --install" when there is no compiler. The result is a linker-signed (ad-hoc) arm64 Mach-O loader that maps the embedded arm64 ELF code. On a Mac without the Command Line Tools this is a first-run blocker and a GUI install prompt, and the loader is code nobody signed. (In CI `cc` exists; the no-compiler path could only be reasoned from the stub text, not run.)
3. **An `.app` whose main executable is the APE does not launch from Launch Services.** `posix_spawn` of the file fails with `Exec format error` (the kernel does not run shell scripts without `#!`, the shell fallback exists only in shells), and `open -W` returns 1. A shell can run it (`./app.com`), so the "ad-hoc signed bundle with the APE as CFBundleExecutable" passes `codesign --verify --deep --strict` but is not a launchable app.
4. **Working structure** (bundle `B`): `Contents/MacOS/<Name>` = a tiny native arm64 launcher (compiled C, 20 lines, `execv`), `Contents/MacOS/ape-loader` = the loader (the compiled `.ape-1.10` binary, or built in CI from the stub's embedded source), `Contents/Resources/app.com` = the fat file (must keep its execute bit; artifacts lose it), `Contents/Info.plist`. Signed inside-out with a (self-signed, locally trusted) code-signing identity, `--options runtime --timestamp` (Apple's time-stamp service was reachable from the runner and the timestamp was embedded), then the bundle. `codesign --verify --deep --strict --verbose=4` passes; **`open -W -n Name.app` (Launch Services) runs it and the app's output is the expected "app: macOS arm64 zip asset: ..."** for every entitlement variant; direct exec works too.
5. **Hardened runtime and entitlements:** the loader signed with the hardened runtime and **no entitlements at all** (ad-hoc, and with the test identity) runs the embedded arm64 program; the executable-memory probe through it gives the same result as without the hardened runtime: map RW, write, `mprotect` RX works; direct RWX mapping is refused (EACCES); `MAP_JIT` RWX and `MAP_JIT` RW->RX work. Adding `allow-jit`, `allow-unsigned-executable-memory`, both, `disable-executable-page-protection` or `disable-library-validation` changed nothing. Caveat: this runner does not demonstrate that the hardened runtime blocks anything for these signatures (the "plain" unsigned control and the hardened one behave alike), so it cannot say which entitlement a Developer ID-signed, notarized build would need for a JIT; the safe plan is to start with none, test the real build, and add `com.apple.security.cs.allow-jit` (MAP_JIT) only if the JIT in the product needs it. Not measured: Developer ID-signed enforcement.
6. **Gatekeeper:** `spctl --assess --type execute` rejects the bare file ("no usable signature"), the ad-hoc bundle (rejected), and the test-identity bundle (`rejected`, `origin=Test Developer ID (CI only)`: spctl names the signer and still rejects; the reason string is only "rejected"). With a quarantine attribute on the self-signed bundle, `open` hung until killed after 40 s (a Gatekeeper dialog that no one can answer in CI). The bare APE with a quarantine attribute ran from a shell with no prompt or error.
7. **Avoiding quarantine:** files fetched by `curl` or Python `urllib` get no `com.apple.quarantine` attribute (empty attribute list); `cp` of a quarantined file keeps it. Quarantine is set by browsers and other quarantine-aware downloaders; it is documented that a launcher such as Steam or itch writing files itself does not set it, but those clients were not run here, only the non-browser download paths above.
8. **Notarization tooling offline:** `xcrun notarytool` 1.1.2, `stapler`, `altool` are present; `notarytool submit` without credentials fails with "No Keychain password item found for profile"; `stapler validate` on an unnotarized bundle says it has no ticket; a `.dmg` of the bundle can be created and signed (`codesign --verify`: valid). `syspolicy_check distribution` reports "Notary Ticket Missing" (Fatal) as expected. `syspolicy_check notary-submission` (the offline pre-check) fails with "Internal Xprotect Error" on **every** bundle including a trivial 1-line C program signed the same way, so on this virtual runner the pre-check does not work and its result says nothing about our files. Real notarization acceptance of this bundle layout is unverified (section 6).
9. Intel Macs: the macOS 15 x86-64 runner runs the file (signed or not, x86-64 slice); `cosmo_dlopen` is "not supported on x86-64 MacOS" (a Cosmopolitan limitation, the arm64 slice loads libSystem fine). A universal launcher (`cc -arch arm64 -arch x86_64`) and the x86-64 loader (`ape-x86_64.macho`, shipped in cosmocc's `bin/`) would be needed for an Intel build of the bundle; not built here.

### Recommended macOS structure
`App.app` as in item 4, with the loader pre-built and signed (so no `cc`, no Command Line Tools, no unsigned runtime-built code), the fat file as a resource, hardened runtime, no entitlements to begin with, Developer ID Application signature, notarized and stapled; shipped in a signed, notarized `.dmg` (or `.zip`). For launcher-based distribution (Steam, itch) the same bundle is fine and quarantine does not apply.

## 4. Linux
Nothing is required by the OS. The file runs unsigned (`sh ./file` and `./file` measured on x64 and arm64). An AppImage-style wrapper adds a FUSE dependency and a second container around a file that already is its own container; not worth it. A detached signature (minisign or GPG over a `SHA256SUMS` file, or Sigstore) published next to the download gives the user a verification path at no cost to the file; the Authenticode signature embedded for Windows is ignored by Linux and does not alter execution (measured). Not measured: any signature-verification client.

## 5. Owner's procedure

### Windows
1. Choose the certificate source. Per Microsoft Learn "Code signing options" (2026-08-29): Azure Artifact Signing (formerly Trusted Signing) about $9.99/month (the Azure pricing page itself did not render prices when fetched, so confirm there), organizations in USA/Canada/EU/UK, individuals USA/Canada, identity validation takes a few business days, no hardware token, works from GitHub Actions; OV certificate from a CA about $150-300/year, worldwide, private key must be on an HSM or hardware token (CA/B Forum rule since June 2023; most CAs offer a cloud HSM); EV about $400+/year and **no longer gives instant SmartScreen reputation** (Microsoft: do not buy it for that). Both OV and Artifact Signing "build reputation over time". Free alternative for open source: SignPath Foundation. Only the first row's price is from Microsoft; the CA prices are Microsoft's stated ranges, not quotes.
2. In CI, after every asset is in the zip: `python pe_prepare_for_signing.py in.com out.exe` (not needed once Cosmopolitan's `ape.S` carries 16 directories, section 1.3), then sign with SHA-256 and an RFC 3161 time stamp (`signtool sign /fd SHA256 /tr <timestamp URL> /td SHA256 ...`, or the Artifact Signing signtool integration / GitHub Action as documented by Microsoft; the exact action name and parameters were not verified here), then `signtool verify /pa /v` and a run of the signed file as the last steps. Do not edit the file after signing. Ship one name for the publisher certificate subject across releases.
3. Expect SmartScreen to warn on early downloads and clear with volume over weeks; do not sign anything that could be flagged; for false positives use the Microsoft Security Intelligence file submission portal; for managed fleets give IT the publisher/hash for WDAC.
4. Distribute through a launcher or the Store where possible (no Mark of the Web, no SmartScreen).

### macOS
1. Join the Apple Developer Program: 99 USD per membership year (Apple's "What's included" page, fetched 2026-10-30). An Apple forum reply from Apple Developer Technical Support (found through search, not confirmed on a page Apple controls) says notarization has no extra fee.
2. Create a "Developer ID Application" certificate (Xcode or the developer portal), export it as .p12 to CI secrets. Create an App Store Connect API key (or an app-specific password) for `notarytool`.
3. Build `App.app` as in 3/item 4 with a pre-built arm64 loader (and universal launcher + `ape-x86_64.macho` if Intel is wanted). Sign inside-out: `codesign --force --timestamp --options runtime -s "Developer ID Application: NAME (TEAMID)" App.app/Contents/MacOS/ape-loader`, the launcher, then the bundle (no `--deep` for signing).
4. `ditto -c -k --keepParent App.app App.zip`; `xcrun notarytool submit App.zip --key AuthKey.p8 --key-id ID --issuer ISSUER --wait`; on failure `xcrun notarytool log <id>`; `xcrun stapler staple App.app`; build and sign the `.dmg`, notarize and staple it too.
5. Verify on a clean Mac (browser download so the quarantine attribute is present): `spctl -a -t exec -vv App.app` ("accepted, source=Notarized Developer ID"), `codesign --verify --deep --strict -vvv`, `xcrun stapler validate`, double-click.
The `notarytool`, `stapler`, `codesign` and `spctl` commands and their failure modes without credentials were exercised in CI; their success paths were not. Apple's own documentation pages could not be retrieved (client-rendered), so requirements such as "hardened runtime, secure timestamp, no get-task-allow" are the commonly documented ones, not re-read from Apple.

## 6. What cannot be closed here
- **Real SmartScreen/Smart App Control reputation**: needs a purchased certificate and real downloads over weeks. Not obtainable in CI. Windows signing mechanics, WDAC treatment and Defender behaviour are closed above.
- **Notarization acceptance** of the bundle (Mach-O-looking bytes and a zip inside a resource file, a runtime-built or pre-built loader, hardened-runtime enforcement, which entitlement a JIT needs once Developer ID-signed): needs an Apple Developer ID certificate and account; one submission would settle it. Offline pre-check (`syspolicy_check`) is unusable on the virtual runner.
- **A Mac without Command Line Tools** (the stub's first-run behaviour): needs a clean Mac or VM; the stub text says it prints an install request.
- **Steam/itch-launcher quarantine behaviour**: only the non-browser download paths were run.
- **signtool `/tr` against a time-stamp server** (local or real): not run.

## 7. Distribution paths for the bare file on macOS (MEASURED 2026-10-30, workflow `platform-distribution`, macOS 26.6 arm64 runner, Apple M1 virtual machine)
Question: can a store serve ONE unmodified Cosmopolitan file and have it start on a Mac without wrapping it in an `.app`, using ad-hoc signing?

**Runner caveat.** The runner is a virtual machine with System Integrity Protection disabled and AMFI developer mode on (`csrutil: disabled`, `security.mac.amfi.developer_mode_status: 1`, `kern.hv_vmm_present: 1`). An unsigned arm64 program ran there, so code-signing enforcement cannot be demonstrated: everything below shows what the tools accept and what Launch Services does with the quarantine attribute, not what a retail Mac's kernel would refuse.

**What the file does at start (read from the stub text, cosmocc 4.0.2):** run `ape` from PATH if present; else run `${TMPDIR:-${HOME:-.}}/.ape-1.10` if it is executable; else (Apple Silicon only) unpack the embedded C source and build the loader with `cc`, printing `please run: xcode-select --install` when there is no compiler.

1. **Ad-hoc signing the bare file does nothing.** `codesign -s -` on the non-Mach-O file stores a "generic" signature in extended attributes (lost by download, zip, `cp -X`); the kernel never evaluates it (it does not execute the file); `spctl` says "no usable signature" for the bare file (section 3).
2. **The ad-hoc signature that matters is on the loader**, a small arm64 Mach-O. It can be added on a server with `rcodesign sign in out` (Linux, no certificate, no Mac): 5 ms for the universal launcher; `codesign --verify --strict` on the Mac then reports "valid on disk, satisfies its Designated Requirement"; `codesign -dvvv` shows `Signature=adhoc`, `CodeDirectory flags=0x2(adhoc)`, sha256 page hashes, embedded; an `.app` signed by `rcodesign` verifies with `--deep --strict` like one signed by `codesign` (sealed resources version 2). It is a fixed small file, so it can be signed once at build time; per-download signing is not needed. Not demonstrated: that a retail Mac's kernel accepts the server-made signature (runner does not enforce).
3. **(A) Bare file + loader put in the stub's place works, with no compiler and no other tool on PATH** (`env -i PATH=/nonexistent`): the unmodified file printed `app: macOS arm64` and read its embedded zip (`/zip/asset.txt`), for a loader signed by `rcodesign` and one signed by `codesign`; also when the bare file carries `com.apple.quarantine`; started as `sh ./bare.com` and by `./bare.com` from zsh; the loader file was unchanged afterwards. So a store client or a one-line installer only has to place the signed loader once.
4. **Launch Services is blocked by quarantine, not by the signature.** `open -W` of the three bundles (unsigned, `rcodesign`-signed, `codesign`-signed): without the quarantine attribute all three returned at once (exit 0); with it all three timed out at 25 s (exit 142: waiting on the Gatekeeper dialog). `spctl --assess` rejected all three ("no usable signature" for the unsigned one, "rejected" for the ad-hoc ones). Started from a shell, the quarantined bundles ran (Gatekeeper does not assess a program started by `exec` from a shell). Ad-hoc signing, server-side or local, does not clear the block.
5. **Browsers quarantine downloads and page storage.** Chrome 155 (real Chrome driven headless by Playwright) set `com.apple.quarantine: 0081;<time>;Chrome;` on the downloaded file; a file the page wrote into its Origin Private File System was stored at `<profile>/Default/File System/000/t/00/00000001`, mode 600, and carries the same attribute. A copy of it marked executable ran from a shell (no prompt on this runner). The File System Access API (`showSaveFilePicker`) exists but needs a user gesture and a native dialog; not driven. Safari was not tested. Conclusion: nothing a web page can do removes the attribute, so "serve the file into browser storage and sign it there" does not avoid Gatekeeper.
6. **(B) A one-time runner app that opens the file as a document** (`runner.m`, 25 lines of Objective-C, ad-hoc signed locally; `CFBundleDocumentTypes` extension `cosmo`; starts the loader on the file): started directly it ran the game (output recorded); through `open -a Runner.app game.cosmo` it ran the game with the document NOT quarantined and with the document QUARANTINED (Launch Services did not block: only the app is assessed, not the document); with the RUNNER itself quarantined (as a browser-downloaded runner would be) it timed out at 25 s and nothing ran, like the bundles. So the gate moves to one app, installed once. Not demonstrated (needs an Apple Developer ID): that the same runner, Developer-ID signed, notarized and stapled, passes Gatekeeper after a browser download, and which hardened-runtime exception the in-memory code needs (`com.apple.security.cs.allow-unsigned-executable-memory` or `allow-jit`).

**Ways to keep the bare file (ranking for a store that serves one unmodified file):**
- **Store client (notarized once) that downloads and starts games.** Files written by a non-browser process get no quarantine attribute (curl and Python urllib: empty attribute list; section 3), so nothing per game is signed or notarized; the client places the signed loader at `~/.ape-1.10` and runs `sh game.com`. The same client covers Windows (SmartScreen only gates files with the browser's mark).
- **One-time runner / document handler (notarized once)** registered for the file extension: double-click works from a plain browser download of the bare file; measured above except notarization.
- **Terminal one-liner** (`curl ... | sh`): no quarantine, bare file, prebuilt ad-hoc loader; no double-click.
- **Notarized `.app` per game** (section 3): works, wraps the file.
- Not options: ad-hoc signing the bare file; signing or storing the file in the browser; a per-download ad-hoc signature (it cannot clear the quarantine block).

**Windows:** same bytes already; browser downloads get Mark-of-the-Web; reputation needs a purchased certificate (section 1, 2, 5).
