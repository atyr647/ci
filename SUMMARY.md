# Summary of the research (state of 2026-11-03)

What was asked: one game file that runs on Windows, macOS and Linux, x86-64 and arm64, with the game logic in WebAssembly and everything else (renderer, runtime, host) in one Cosmopolitan "fat" executable. Everything below was measured on CI runners (shared machines; real GPUs were not available: the adapters are software ones, Metal is the runner's virtual Apple GPU). Details and numbers are in `FINDINGS.md` (parts 1-11); the owner's decisions are marked **Decision**.

## Architecture that came out of it
- **One file, five targets.** A Cosmopolitan fat file holds the x86-64 and arm64 halves; Linux x86-64/arm64, macOS arm64, Windows x86-64 run it directly. Windows arm64 has no Cosmopolitan half (the x86-64 half runs under emulation): **Decision:** a small native arm64 host is the route there (spike done, below).
- **Game logic in wasm, run by a static Wasmtime** (runtime-only, no_std, our own platform layer, precompiled `.cwasm` files embedded in the file). Feature coverage on all five targets: core wasm, GC, exceptions, memory64, relaxed SIMD, WASI 0.1 and 0.2, async, threads (shared memory, atomics, wait/notify, thread spawn). On arm64 the patched Cranelift never allocates x28 (Cosmopolitan's thread register); the Rust parts reserve x28 and x18.
- **Renderer: Dawn compiled by Cosmopolitan** (Vulkan on Linux; D3D12 in the file for Windows; Metal in the file for macOS). Speed against native Dawn is in `FINDINGS.md` part 11: equal or better on most rows; buffer creation on Linux x86-64 is 0.66x and on Linux arm64 0.79x.
- **Complete game loop, wasm to GPU (workflow `gameloop`, `game/`).** A wasm guest (1,024 GPU particles by compute shader, an instanced render into 256x256, scripted input, audio tone) runs under the host with Wasmtime and Dawn: `RESULT PASS` on all five targets (compute checked against a CPU reference, render probes, scripted input, audio). Windowing, input and audio mechanics were proven per OS by probes (`platform-io`, all five pass); they are not yet connected to Dawn surfaces or to a real-time audio device.
- **Software Vulkan inside the file, Linux x86-64 and arm64 (workflows `swiftshader-cosmo`, `icd-test`).** SwiftShader built with Cosmopolitan's compiler is linked into the file and used when no system Vulkan loader opens (or `DAWN_COSMO_VK=software`): the whole game loop passes in an Alpine container with no glibc and no Vulkan library, and the automatic fallback passes with the system loader removed. Real GPU drivers on glibc systems still use the glibc helper. No speed claim: the host frame time does not wait for GPU completion.
- **Hot numeric kernels as host imports** (AVX2+FMA, AVX-512F, NEON, plain fallback, chosen at start-up): 1.3x (macOS) to 6.4x (AVX-512) faster than wasm SIMD128 for a 256x256 matmul. **Decision:** this is the route to 256/512-bit; Cranelift has no 256-bit lowering and no other engine tried widens automatically.
- **CPU-level modules:** `.cwasm` compiled for the baseline and for x86-64 AVX2/FMA/BMI (v3); the host picks v3 when the CPU and OS support it and the machine is not an ARM64 machine emulating x86-64 (v3 is slower there).
- **Distribution:** **Decision:** Linux ships the single unmodified file (no AppImage, no package); the game store ships bare files; APFS compression of the file is off by default; NTFS (LZX) compression is free and saves 2.6x on disk. Code stays uncompressed inside the file (decompressing at start costs +130 ms); transfer compression (xz/zstd with the x86/arm64 filter) gives 0.25-0.30 of the size.

## Defects found by this work and closed (each with a check that failed before)
x86-64 v3 modules did not load (CPU-feature hook incomplete); arm64 driver calls blocked all signals twice per call (454 ns) - raw calls are now safe on threads that keep asynchronous signals blocked; Cosmopolitan's 80 KiB default thread stack overflowed in the driver; the driver's C library had no thread block on threads the C library created (x86-64 crash, arm64 heap corruption, hang on a created render thread) - fixed with a pool of parked library threads whose thread blocks are borrowed per foreign call; macOS register x18 clobbered by the kernel inside the Rust runtime (intermittent wrong results); the wasm-threads guest was linked with a private memory per thread; Windows NTFS compression measured on a drive that cannot compress; the benchmark's float loop was compiled at -O2 against -O3; the benchmark runner could hang for 35 minutes on a killed process.

## What a host must do (requirements that came out of the measurements)
1. On Linux, call `DawnCosmoForeignInit()` on the main thread at start-up, before any other thread calls the driver (it makes the 64 parked thread blocks and preloads the Vulkan loader). A process can have at most 64 threads that call the driver.
2. Threads that call the driver keep asynchronous signals blocked (done automatically on the first driver call of a thread; the main thread of an arm64 host that wants raw driver calls calls `DawnCosmoGpuThreadEnter()` and must take its signals at safe points).
3. Create threads through `pthread_create` with the wrapper in `ci-webgpu-test/win_shield.h` (8 MiB stacks).
4. Cosmopolitan 4.0.2 compiles a 478-byte helper with the system's `cc` the first time a driver is loaded on Linux; without a compiler the GPU was not found (measured). The Dawn patch now embeds a helper built ahead of time (Ubuntu 20.04 container, glibc 2.31; x86-64 and arm64) and writes it into `$TMPDIR/.cosmo/` before the first load: a machine without a compiler and with an empty cache finds the adapter on both architectures (measured end to end), and the helper itself loads a plain library with no compiler on Ubuntu 20.04, Debian 11 and Ubuntu 24.04 on both architectures. musl-based distributions (Alpine): the glibc helper does not work there, but the in-file software driver does (game loop passes in Alpine on both architectures, see below); real GPU drivers on musl systems are not available.

## What is not finished (stated plainly)
- **Dawn gaps after the fixes (mutex fast path in every program, both halves built by clang with libc++ hardening off, two small Tint token patches, mimalloc as the malloc of the file):** the buffer-create gap is explained and closed (parts 13 and 14 of `FINDINGS.md`): the driver's heap grew by about 2.6 MB during the first burst of buffer creation because Dawn's frees go to this file's malloc; populating it before the burst removes the cost; per call the file is as fast as or faster than native. Shader-module compile (160 functions) is at native speed or better everywhere: Linux x86-64 5.93 ms against 5.98 native, arm64 4.57 against 4.9 (faster), Windows x64 2.4x faster than native Dawn, macOS about equal. The last x86-64 cost was a store-forwarding stall: libc++'s `std::optional` writes one byte of its storage, and Tint's lexer then loaded a 4-byte token type from the same address; a one-byte enum type removes it. All gates pass on all five targets with this build (compute check, `dlopen-nocc`, `dlopen-helper`, `dawn-thread-diag`; every benchmark round exits 0: Linux 441 runs, macOS 198, Windows 369). **What is left on Dawn speed:** the one-time ~0.9 ms of page faults at the first burst of buffer creation, which follows from Dawn and the driver having separate heaps (per call the file is as fast as native or faster). **Closed in part 14 of `FINDINGS.md`:** the host calls `DawnCosmoWarmDriverHeap()` right before the burst (1.5 ms once); the first burst of 4,000 buffers then takes 15-17 page faults (native Dawn 256) and runs at or ahead of native Dawn on Linux x86-64 and arm64. The earlier statement that pre-faulting does nothing was wrong (`calloc` does not write fresh memory) and is corrected there.
- **Dawn on old Linux distributions:** Ubuntu 20.04 and Debian 11 (Mesa 21.2 / 20.3) give no Vulkan adapter for Dawn even with a compiler installed; so far only Ubuntu 24.04 was run with Dawn. What the minimum Mesa/driver version is was not measured.
- **Windows 11 ARM:** shipped in the file as native arm64 programs that the x86-64 half unpacks and runs on ARM64 machines: the wasm host (1.2-2.6x faster than emulation, same output) and the Dawn D3D12 benchmark (process total 1.00x of native Dawn against 0.89x for the emulated half). The unpacked executables are unsigned (signing held by the user).
- **Software Vulkan for Linux arm64:** done and measured (SwiftShader LLVM backend built by Cosmopolitan's compiler, linked into the file): driver-only test and the complete game loop pass on real arm64 machines, including in an Alpine musl arm64 container with no glibc and no Vulkan library, and the automatic fallback works. Same limits as x86-64: software only, no GPU speed claim, real GPUs on glibc systems still go through the glibc helper.
- **Done in part 14 (2026-11-03), measured on CI runners:** windows, keyboard and pointer without libraries on all five targets (X11 and Wayland by their protocols, GDI, AppKit); the frames of the game shown in a window (`--present`); a real-time audio ring (60 frames a second, 96,000 frames in, 96,000 out, 0 dropped, 0 under-runs on all five targets) with back ends for PulseAudio (native protocol, no library, also PipeWire), ALSA, AudioQueue and waveOut; gamepads (Linux evdev tested with uinput, 11 of 11 events; XInput and GameController load and report no controller); per-frame GPU completion time and GPU timestamps on all five targets; real GPU drivers on musl systems (Alpine's own Mesa, helper picked automatically); the software fallback now also starts when a Vulkan loader exists but no driver; executable-memory policies (Pulley interpreter, nothing worked around).
- **Not tested because no device exists on the CI machines (needs hardware or a decision, see below):** real GPUs (D3D12, Metal, Vulkan on NVIDIA/AMD/Intel), a sound card (Windows waveOut and WASAPI, ALSA hardware), controllers on Windows and macOS (XInput and GameController answered "no controller" only), SELinux execmem denial (cannot be enforced on the CI machines) and the macOS hardened runtime of a notarised app (an ad hoc signature restricts nothing; needs the owner's Developer ID). **Checked and failing:** no Cosmopolitan program, the game file included, starts on Windows under arbitrary code guard (exit code 11 before any of our code runs); ACG is only applied when a program asks for it or an administrator sets it for that executable.
- **Software GPU speed:** the driver inside the file renders correctly but takes 10-60 ms per frame for the demo scene (lavapipe 0.5-1 ms); the LLVM backend on x86-64 is no faster than Subzero, and Chromium's own SwiftShader on the same machine takes the same time (28-32 ms against 22-29 ms for the build in the file): the speed is SwiftShader's (many small task hand-offs between threads), not an effect of this build. Presentation is by CPU read-back (about 0.3 ms per 256x256 frame on Linux, grows with frame size); a swapchain path through Dawn surfaces is a recorded optimisation, not built.
- **Windows 11 ARM running the same file the same way:** needs an arm64 Windows target in Cosmopolitan itself (start-up, TEB/TLS, NT calls); checked, not possible without that port.
- **Held by the owner, not started:** the store client, signing and notarisation (needs an Apple Developer ID secret and a Windows certificate), cleanup of the earlier engine branches in the public repository.
