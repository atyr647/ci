# Summary of the research (state of 2026-10-31)

What was asked: one game file that runs on Windows, macOS and Linux, x86-64 and arm64, with the game logic in WebAssembly and everything else (renderer, runtime, host) in one Cosmopolitan "fat" executable. Everything below was measured on CI runners (shared machines; real GPUs were not available: the adapters are software ones, Metal is the runner's virtual Apple GPU). Details and numbers are in `FINDINGS.md` (parts 1-11); the owner's decisions are marked **Decision**.

## Architecture that came out of it
- **One file, five targets.** A Cosmopolitan fat file holds the x86-64 and arm64 halves; Linux x86-64/arm64, macOS arm64, Windows x86-64 run it directly. Windows arm64 has no Cosmopolitan half (the x86-64 half runs under emulation): **Decision:** a small native arm64 host is the route there (spike done, below).
- **Game logic in wasm, run by a static Wasmtime** (runtime-only, no_std, our own platform layer, precompiled `.cwasm` files embedded in the file). Feature coverage on all five targets: core wasm, GC, exceptions, memory64, relaxed SIMD, WASI 0.1 and 0.2, async, threads (shared memory, atomics, wait/notify, thread spawn). On arm64 the patched Cranelift never allocates x28 (Cosmopolitan's thread register); the Rust parts reserve x28 and x18.
- **Renderer: Dawn compiled by Cosmopolitan** (Vulkan on Linux; D3D12 in the file for Windows; Metal in the file for macOS). Speed against native Dawn is in `FINDINGS.md` part 11: equal or better on most rows; buffer creation on Linux x86-64 is 0.66x and on Linux arm64 0.79x.
- **Hot numeric kernels as host imports** (AVX2+FMA, AVX-512F, NEON, plain fallback, chosen at start-up): 1.3x (macOS) to 6.4x (AVX-512) faster than wasm SIMD128 for a 256x256 matmul. **Decision:** this is the route to 256/512-bit; Cranelift has no 256-bit lowering and no other engine tried widens automatically.
- **CPU-level modules:** `.cwasm` compiled for the baseline and for x86-64 AVX2/FMA/BMI (v3); the host picks v3 when the CPU and OS support it and the machine is not an ARM64 machine emulating x86-64 (v3 is slower there).
- **Distribution:** **Decision:** Linux ships the single unmodified file (no AppImage, no package); the game store ships bare files; APFS compression of the file is off by default; NTFS (LZX) compression is free and saves 2.6x on disk. Code stays uncompressed inside the file (decompressing at start costs +130 ms); transfer compression (xz/zstd with the x86/arm64 filter) gives 0.25-0.30 of the size.

## Defects found by this work and closed (each with a check that failed before)
x86-64 v3 modules did not load (CPU-feature hook incomplete); arm64 driver calls blocked all signals twice per call (454 ns) - raw calls are now safe on threads that keep asynchronous signals blocked; Cosmopolitan's 80 KiB default thread stack overflowed in the driver; the driver's C library had no thread block on threads the C library created (x86-64 crash, arm64 heap corruption, hang on a created render thread) - fixed with a pool of parked library threads whose thread blocks are borrowed per foreign call; macOS register x18 clobbered by the kernel inside the Rust runtime (intermittent wrong results); the wasm-threads guest was linked with a private memory per thread; Windows NTFS compression measured on a drive that cannot compress; the benchmark's float loop was compiled at -O2 against -O3; the benchmark runner could hang for 35 minutes on a killed process.

## What a host must do (requirements that came out of the measurements)
1. On Linux, call `DawnCosmoForeignInit()` on the main thread at start-up, before any other thread calls the driver (it makes the 64 parked thread blocks and preloads the Vulkan loader). A process can have at most 64 threads that call the driver.
2. Threads that call the driver keep asynchronous signals blocked (done automatically on the first driver call of a thread; the main thread of an arm64 host that wants raw driver calls calls `DawnCosmoGpuThreadEnter()` and must take its signals at safe points).
3. Create threads through `pthread_create` with the wrapper in `ci-webgpu-test/win_shield.h` (8 MiB stacks).
4. Linux needs a C compiler on the user's machine the first time the GPU driver is loaded (Cosmopolitan compiles a 478-byte helper with `cc`). Without one the GPU is not found (measured). A helper built ahead of time and placed in `$TMPDIR/.cosmo/` before the first load works without a compiler on current glibc (measured, both architectures) - see "open".

## What is not finished (stated plainly)
- **x86-64 Linux buffer create+release is 0.66x of native (about 0.4 us each).** Not explained: user time, system-call count and page-fault count per iteration are equal or lower in the Cosmopolitan build, only system time is higher; allocator, lock, compiler and trampoline were each ruled out. Absolute cost: 0.4 ms per frame for 1,000 buffers.
- **Pre-built dlopen helper on old Linux distributions** and shipping it inside the file: the compiler-less machine works on glibc 2.39 for both architectures; the check on glibc 2.31 distributions was inconclusive because their Mesa has no usable Vulkan adapter for Dawn (control with a compiler fails the same way); see `FINDINGS.md`. The embedding and the first-start extraction are not written.
- **Windows 11 ARM:** the native host runs the wasm and the NEON kernels (1.2-2.6x faster than emulation); the Dawn D3D12 part is measured natively on win-arm64 in the benchmark but has not been linked into that host.
- **Held by the owner, not started:** the store client, signing and notarisation (needs an Apple Developer ID secret and a Windows certificate), cleanup of the earlier engine branches in the public repository.
