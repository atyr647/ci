Cause and fix (measured, both arm64 failures vanished together): on aarch64 Cosmopolitan keeps its thread pointer in register x28. Wasmtime's code may use x28 for anything, so when it calls a host function written in Cosmopolitan C, that C code runs with a garbage thread pointer (the first `printf` in the callback hung on macOS or crashed on Linux). The callback now saves Wasmtime's x28, restores Cosmopolitan's own on entry and puts Wasmtime's back on return (`TLS_ENTER`/`TLS_LEAVE` in `ci-wasm-host/wt-host.c`). This applies to ANY callback from foreign code into Cosmopolitan code on aarch64, including Dawn-to-Vulkan callbacks.

## Windows: what blocked Dawn, found one by one (all measured)
1. The Vulkan loader on Windows ignores VK_ICD_FILENAMES / VK_DRIVER_FILES when the process is elevated (GitHub's Windows runners are). A software driver (Mesa lavapipe) must be registered under `HKLM\SOFTWARE\Khronos\Vulkan\Drivers` (value name = path of the ICD json, DWORD 0). With that, a native Python process sees 1 physical device, and the Cosmopolitan probe (`ci-webgpu-test/vkprobe.c`) passes on Windows x64: loads `vulkan-1.dll`, calls it with the Microsoft ABI, finds llvmpipe.
2. Cosmopolitan on Windows turns every unknown SEH exception into a fatal SIGSEGV, including DBG_PRINTEXCEPTION_C (0x40010006) that `OutputDebugString` raises (the loader with VK_LOADER_DEBUG, Dawn's logging, many DLLs). A first-in-line vectored exception handler returning EXCEPTION_CONTINUE_EXECUTION for 0x40010006 / 0x4001000A / 0x406D1388 fixes it (`ci-webgpu-test/win_shield.h`). Verified in the probe: without the shield the process dies at the first loader log line, with it the run continues.
3. GCC miscompiled the run-time switch `IsWindows() ? ms_abi_call(args) : sysv_call(args)`: the disassembly of the compiled wrapper shows ONE call with System V registers and a tail `jmp`; the Microsoft branch was dropped (its call-merging does not compare the calling convention). On Linux/macOS the surviving System V call is the right one, on Windows every Vulkan call arrived with the wrong registers (the crash report showed a garbage handle in RCX). Earlier symptom on Linux: the 10th call of a sequence failed when the wrapper was inlined. Fix in `dawn-cosmo/patch.py`: out-of-line wrapper plus two differently worded asm statements so the branches cannot be merged. Verification in CI pending at the time of writing.

## Wasmtime INSIDE the Cosmopolitan file, wasm threads, wasm SIMD, Tint as wasm (measured 2026-10-30, Wasmtime v50.0.0, cosmocc 4.0.2)

**Wasmtime linked into the executable (workflow `wasmtime-bundle`, job `static-link`).** `libwasmtime.a` is built from source for the Rust musl target (C parts with the Cosmopolitan compiler) and linked with the host into one Cosmopolitan executable: no dlopen, no extraction.
- Needed: stubs for the Linux calls Cosmopolitan lacks (`epoll_*`, `eventfd`, `mkfifo`, `waitid`; `ci-wasm-host/static-stubs.c`); Rust's I/O reactor (mio) built with `--cfg mio_unsupported_force_poll_poll --cfg mio_unsupported_force_waker_pipe` so it uses poll(2) and a pipe instead of epoll/eventfd (the eventfd stub's ENOSYS reached Rust's error formatting and crashed - found with gdb on the CI artifact: `mio::Selector::new -> eventfd`). Cosmopolitan's own `strerror_r` already has the POSIX (XSI) form (measured: returns 0 and fills the buffer), so nothing is replaced there; two earlier attempts at "fixing" it (a redefinition, then `--wrap`) only added crashes (infinite recursion through Cosmopolitan's `strerror`).
- Result on Linux x86-64: **PASS** - the host loads the wasm guest, the guest calls the host import, the host answers, exit code 0 (run 8, commit 6d9b73e).
- The same code in the fat file (x86-64 + arm64, `static-fat`) on the other four targets (run 9, commit 9be6b72): **FAIL on all four, each for a different reason, all from one cause.** Rust's standard library and its `libc` crate are compiled for the Linux musl target, so they pass **Linux's numeric constants** (clock ids, `getrandom` flags, errno values, mmap/open flags, signal numbers) to Cosmopolitan's C library, which on every other OS expects *its own run-time constants* for that OS. Measured:
  - macOS arm64: `Timespec::now` -> `clock_gettime(1, ...)` returns EINVAL (1 is Linux's CLOCK_MONOTONIC, macOS's is 6) -> `unwrap()` panic during `wasm_engine_new`/`store_new`.
  - Windows x64: `getrandom(buf, n, flags=4)` (GRND_INSECURE, Linux number) -> `errno=87` -> panic in `std::sys::random` during `wasm_engine_new`.
  - Linux arm64: panic "strerror_r failure" while module compilation (some earlier call fails; the original error is hidden behind this one - not diagnosed, no debugger for arm64 here).
  - Even if each of those were translated, macOS arm64 would still not be able to run Wasmtime's JIT: code compiled for `*-linux-musl` does not use `MAP_JIT` / `pthread_jit_write_protect_np`, which Apple Silicon requires for executable memory; the official macOS library does.
  So "Wasmtime (JIT) statically linked into the Cosmopolitan file" works where the host really is Linux x86-64 and nowhere else without a translation layer of unknown size. What does work on all five targets today is the **bundled** form (the four official libraries stored inside the executable, extracted to a temp file at first use, `cosmo_dlopen`ed: run 9 `bundled-test`, 5/5 PASS).
- Option that makes one implementation really static on every OS: Wasmtime's **custom-platform / no_std** build (docs: "Building Wasmtime for a Custom Platform"): no Rust std, no libc crate; the embedder supplies ~20 C functions (mmap/mprotect, TLS, locks, fibers; compiled by Cosmopolitan, so with the right constants). Costs, from the same page: **no Cranelift/Winch** (modules must be precompiled to `.cwasm` for the exact Wasmtime version and CPU target, one per architecture), **no WASI**, `signals-based-traps` off (explicit bounds checks, slower), nightly Rust and a custom target. Not tried here.
- aarch64: the static link itself works (Rust std rebuilt with x28 reserved, Cosmopolitan keeps its thread pointer there).

## D3D12 backend compiled INTO the Cosmopolitan file; Metal sources compile; GPU-choice tool (measured 2026-10-30, workflow `dawn-cosmo`, run 41022592962)

- How: Dawn's D3D/D3D12 translation units are compiled as "Windows" (`DAWN_COSMO_AS_WINDOWS`) against Wine's headers plus Microsoft's DirectX-Headers, everything else stays POSIX-flavoured in the same binary. Classes shared by both flavours (`SystemHandle`, `SystemEvent`, `WaitAnySystemEvent`, `DynamicLib`) choose Windows or POSIX behaviour when the program runs. ~14 Win32 functions Dawn uses are provided by `Win32Shim.cpp`.
- Three root causes found one by one (each needed its own check):
  1. **C++ exceptions are fatal:** Cosmopolitan installs a first-in-line vectored exception handler that turns any unknown SEH exception (MSVC C++ throw = 0xE06D7363, used inside D3D12/DXGI/FXC) into a process kill. `win_shield.h` puts a handler ahead of it that passes those through.
  2. **Thread stack limits:** the Windows thread block (TEB) holds the stack bounds of the thread's *Windows* stack; Cosmopolitan runs the program on its own stacks, so exception dispatch inside D3D12CreateDevice found the stack pointer outside the bounds and the process died silently (no crash report). Fix: point the TEB stack base/limit at Cosmopolitan's stack, for the main thread and every created thread (`--wrap=pthread_create`).
  3. **Struct-returning COM methods:** MSVC passes (this, result pointer, args); GCC with ms_abi passes (result pointer, this, args). `GetResourceAllocationInfo` and 29 similar virtuals returned garbage and crashed in D3D12Core. `fix_com_struct_returns.py` rewrites the 30 declarations in d3d12*.h to the MSVC order.
- Correction: an earlier "D3D12 build success" was a stale cached library (the build step passed although objects had failed). The build step now fails on any `FAILED:` line; the successes above are from clean builds.

## Session of 2026-10-30 (part 3): Metal in the file, Dawn Cosmopolitan vs native, why the file cannot be code-signed (measured in CI)
**Metal backend compiled INTO the Cosmopolitan file works on macOS 26 arm64** (workflow `dawn-cosmo`, run 41034054904; backend id 5, "Apple Paravirtual device", hash `9761e8ede774e783` like every other backend). **Dawn compiled by Cosmopolitan vs native Dawn** (workflow `dawn-bench`, same source `dawn_bench.cpp`, interleaved rounds, a second native run as the noise floor; CI runners have no GPU, so this is the CPU side plus software/virtual adapters):

Cause measured in isolation (`alloc-probe`, reproduced locally): Cosmopolitan's C library takes **29-45 ns per malloc/free pair vs 7-10 ns** (glibc), **14-21 ns per uncontended mutex lock/unlock vs 4-6 ns**, and with 4 threads **~400 ns per allocation vs ~13 ns** (one global lock). Dawn allocates and locks constantly. Fix tried: a 60-line per-thread small-block cache behind `operator new/delete` (`alloc-probe/tcache_new.cpp`): 4.1 ns single-threaded and 9.2 ns on 4 threads in the probe (native 11.4 / 12.7). Linked into every fat executable from now on; its effect on Dawn is to be read from the next `dawn-bench` run. The mutex cost remains.
- macOS arm64 (Metal on a virtual M1, 5 rounds, noise floor up to ~20% and larger on start-up): Tint parse 7.5 vs 9.5 ms (0.79x), pipeline 25.4 vs 21.3 ms, buffer create equal, command recording 35.8 vs 14.8 us (**Cosmopolitan 2.4x faster, confirmed by the native repeat, cause unknown**), submit+map 1.02 vs 0.93 ms, readback 7.2 vs 7.7 GB/s; adapter request 31 vs 58 ms (framework loading and the Objective-C shim). GPU-kernel and memcpy rows on this run are invalid (the compiler removed the native memcpy; the virtual GPU's kernel timing is implausible) and are not used.
- Windows: native Dawn built with MSVC returns "no device" on the runner in this benchmark (the Cosmopolitan build gets a device); being diagnosed, so no Windows comparison yet.

**Why the Cosmopolitan file cannot be code-signed on Windows** (platform-probes): the PE header inside the file declares 2 data directories (`NumberOfRvaAndSizes = 2`, optional header 128 bytes) and a Mach-O header follows it directly; signing needs the 5th directory (certificate table). `Set-AuthenticodeSignature` says "not a valid Win32 application", `signtool` 0x800700C1, `osslsigncode` a PKCS7 decoding error. `platform-probes/pe_prepare_for_signing.py` writes a second PE header with 16 directories into zero padding (offset 0x1000) and points `e_lfanew` at it; the file still runs on Linux; whether Windows accepts and signs it is the next probe result.

**Wasm compiled to C ahead of time (wasm2c from wabt 1.0.37 + GCC -O3) vs Wasmtime's JIT** (linux x64, relative to native scalar): matmul SIMD 0.46-0.47x (Wasmtime 0.65x), scalar 0.10-0.12x (Wasmtime 0.16x), n-body 0.52-0.55x (Wasmtime 0.51x), transform 0.76x base ISA / 1.03x host ISA (Wasmtime 1.14x), sort 1.18x, hash 1.0x; bytecode-interpreter kernel 0.79x (wasm2c host-ISA build) vs 0.40x (Wasmtime, SIMD build). wasm2c does not support relaxed SIMD. So translating wasm to C does not beat the JIT in general and does not recover native auto-vectorisation; what it removes is the need for a JIT and executable memory.

## Session of 2026-10-31 (part 11): AVX2/FMA/NEON wiring, driver calls on arm64 without the signal-blocking trampoline, threads that the C library creates, macOS register x18, wasm threads, native Windows 11 ARM host, file-system compression (all measured in CI; runners are shared, so the machine under a run changes between runs)
**SIMD wiring (x86-64 AVX2/FMA/BMI modules chosen at start-up, native kernels as imports).**
- *Defect found and closed:* the first x86-64 v3 modules did not load on any runner ("failed to detect if target-specific flag cmpxchg16b is available"): the host-feature hook answered only some of the flags Wasmtime asks for. The hook now answers all of them (sse3 .. avx512 variants, cmpxchg16b, avxvnni, lzcnt, bmi), and the host falls back to the baseline module if the engine still refuses a v3 one. The kernel step had `continue-on-error` and printed empty tables, so it looked green; it now fails loudly.
- *Native kernels vs wasm SIMD128, 256x256 matmul, microseconds (wasm SIMD128 / native import):* Linux x64 AVX-512 runner (EPYC 9V45) 917 / 142 (6.4x; the AVX2 kernel on the same machine 269, so AVX-512 is 1.9x faster than AVX2 there); Linux x64 AVX2 runner 1428 / 450 (3.2x); Windows x64 1399 / 398 (3.5x); Windows arm64 with the x86-64 half emulated (AVX2 offered by the emulator) 2186 / 1457 (1.5x); Linux arm64 NEON 1781 / 911 (2.0x); macOS arm64 NEON 889 / 669 (1.3x). The outputs agree to about 1e-6 in every case.
- *v3 modules vs baseline modules (shootout kernels, ms, Linux x64 EPYC):* SIMD matmul 2.06 vs 2.66 (22% faster), transform 0.29 vs 0.41 (29%), scalar interpreter kernel 216 vs 273 (21%), n-body equal, but the interpreter kernel written with SIMD128 is 342-348 vs 311 (about 10% slower with v3). - *256-bit:* CLIF defines 256/512-bit vector types (I32X8, F32X8, I8X32, F32X16) but the x86-64 backend lowers vectors of at most 128 bits, so Cranelift emits AVX2/FMA encodings for SIMD128 but never a 256-bit operation. Probes of other engines: V8's revectorizer widened a loop of one v128 operation (151.8 -> 97.9 ps per float) and left unrolled loops (95-112 ps without it) and matmul unchanged; Wasmer LLVM, WAMR AOT and w2c2+SIMDe do not widen either. Real 256/512-bit work today means the native-kernel imports (decision: that is the route).
**Linux arm64 buffer-create slowness: cause, fix, and what makes the fix safe.**
- cosmo_dltramp on arm64 is a trampoline that blocks ALL signals with two rt_sigprocmask system calls around every foreign call (454 ns per call; the same call through a raw pointer 1.8 ns). On x86-64 Cosmopolitan 4.0.2 returns the function itself (no thunk).
- Why it exists: foreign code may use x28, Cosmopolitan's thread register on arm64, as an ordinary register, so a Cosmopolitan signal handler that runs inside it reads thread-local storage through garbage. Measured in a harness (`direct-call`, a foreign library whose function keeps a counter in x28, 1 ms SIGALRM storm): calling the raw pointer with signals open dies with SIGSEGV; through the trampoline, with the thread's asynchronous signals blocked (the signals go to another thread: 2000 of 2000), or with the signals taken at safe points with sigtimedwait (2000 of 2000): all work.
- Fix in the Dawn patch: raw calls only on threads that keep asynchronous signals blocked (DawnCosmoGpuThreadEnter, synchronous faults stay unblocked); every other thread keeps the trampoline. buffer create+release 2.67 -> 1.07-1.11 us (native 0.82-0.87), bindgroup 3.88 -> 3.36, submit+map 43.8 -> 37.6 us (native 37.7). The gate costs 0 ns measured.
**Threads created by the C library, on Linux (found by running the whole benchmark on a std::thread and Dawn's async pipeline creation; native passes both).** Four separate defects, found one by one with gdb on the linker's .dbg file and a small harness:
1. Cosmopolitan's default thread stack is about 80 KiB: "Stack Overflow" in vkCreateDevice and in Dawn's worker threads on every OS. The thread-creation wrapper now gives every thread at least 8 MiB (reserved, touched lazily).
2. The driver is loaded with the system C library, which initialises per-thread state (locale and ctype pointers, errno, malloc cache) in a thread block that only its own pthread_create makes. A Cosmopolitan-made thread has none: on x86-64 libc.so.6 read a null ctype table (SIGSEGV; errno and creating a thread crash too); on arm64 the library's thread-local variables start at tp+0x10 and overlay Cosmopolitan's own (they start at tp+0x28), which corrupts Cosmopolitan's allocator state (the "corrupted chunk header in operator new" crash). Measured with a battery of ordinary libc use from the main thread vs a created thread (ctype, malloc, errno, formatting, mutex, once, pthread_self, foreign thread create/join): created threads crash in 3-4 of 8 tests on x86-64 and 2 of 8 on arm64.
3. Rejected designs, with the measurement: threads made by the foreign pthread_create share the main thread's Cosmopolitan TLS block on x86-64 (all four threads report the same TIB; thread-locals are not per thread) and crash on arm64; calling uselocale(LC_GLOBAL_LOCALE) at thread start fixes ctype and formatting on both but not errno or thread creation on x86-64.
4. **Fix (validated on both architectures in the harness: 8 of 8 tests pass; then in Dawn):** the main thread makes a pool of 64 parked threads with the library's own pthread_create (signals blocked, sleeping); a thread that calls into foreign code takes one parked thread's thread block and puts its thread pointer there (wrfsbase / arch_prctl on x86-64, tpidr_el0 on arm64) for exactly the duration of each foreign call, with asynchronous signals blocked on that thread. Details that mattered: on x86-64 the pointer must be read from the register (rdfsbase), not from %fs:0, which Cosmopolitan code sees as its own TIB; on arm64 Cosmopolitan code cannot read the library's value, so each parked thread runs nine instructions that publish its own tpidr_el0 and block in ppoll; foreign pthread_create cannot be called from a created thread on x86-64, so the pool is made ahead of time on the main thread (the host calls DawnCosmoForeignInit at start-up); the Vulkan loader and vkGetInstanceProcAddr are loaded by the main thread and handed out without a foreign call (cosmo_dlopen/dlsym are mostly Cosmopolitan code and cannot be wrapped).
- Result, final build (7 rounds, 5 targets): Dawn async pipeline creation with worker threads, with the library's own lock and with both alternative lock builds, async with tasks on the posting thread, and the whole benchmark on a created thread all exit 0 on Linux x64, Linux arm64, macOS arm64, Windows x64 and Windows arm64 (before: crash on both Linux architectures, hang at exit on a created render thread). The hang on a created render thread (x86-64: the process did not end after the benchmark had finished, the main thread waiting in pthread_join for it; arm64: stuck right after instance creation, the render thread in a futex wait on a contended lock, value 2, inside a 128 KiB anonymous mapping of the driver stack) is gone with the fix. The lock holder was not identified, so the link between the two is an observation (it does not occur once foreign calls run on a library-owned thread block), not a traced cause.
**macOS arm64: intermittent wrong results in the Rust runtime (closed).** The kernel guest failed 18 of 25 runs on one build and about 7% of runs on another, in every execution mode including the interpreter, with a host callback not finding the module's "memory" export.
