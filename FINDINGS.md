Cause and fix (measured, both arm64 failures vanished together): on aarch64 Cosmopolitan keeps its thread pointer in register x28. Wasmtime's code may use x28 for anything, so when it calls a host function written in Cosmopolitan C, that C code runs with a garbage thread pointer (the first `printf` in the callback hung on macOS or crashed on Linux). The callback now saves Wasmtime's x28, restores Cosmopolitan's own on entry and puts Wasmtime's back on return (`TLS_ENTER`/`TLS_LEAVE` in `ci-wasm-host/wt-host.c`). This applies to ANY callback from foreign code into Cosmopolitan code on aarch64, including Dawn-to-Vulkan callbacks.

## Windows: what blocked Dawn, found one by one (all measured)
1. The Vulkan loader on Windows ignores VK_ICD_FILENAMES / VK_DRIVER_FILES when the process is elevated (GitHub's Windows runners are). A software driver (Mesa lavapipe) must be registered under `HKLM\SOFTWARE\Khronos\Vulkan\Drivers` (value name = path of the ICD json, DWORD 0). With that, a native Python process sees 1 physical device, and the Cosmopolitan probe (`ci-webgpu-test/vkprobe.c`) passes on Windows x64: loads `vulkan-1.dll`, calls it with the Microsoft ABI, finds llvmpipe.
2. Cosmopolitan on Windows turns every unknown SEH exception into a fatal SIGSEGV, including DBG_PRINTEXCEPTION_C (0x40010006) that `OutputDebugString` raises (the loader with VK_LOADER_DEBUG, Dawn's logging, many DLLs). A first-in-line vectored exception handler returning EXCEPTION_CONTINUE_EXECUTION for 0x40010006 / 0x4001000A / 0x406D1388 fixes it (`ci-webgpu-test/win_shield.h`). Verified in the probe: without the shield the process dies at the first loader log line, with it the run continues.
3. GCC miscompiled the run-time switch `IsWindows() ? ms_abi_call(args) : sysv_call(args)`: the disassembly of the compiled wrapper shows ONE call with System V registers and a tail `jmp`; the Microsoft branch was dropped (its call-merging does not compare the calling convention). On Linux/macOS the surviving System V call is the right one, on Windows every Vulkan call arrived with the wrong registers (the crash report showed a garbage handle in RCX). Earlier symptom on Linux: the 10th call of a sequence failed when the wrapper was inlined. Fix in `dawn-cosmo/patch.py`: out-of-line wrapper plus two differently worded asm statements so the branches cannot be merged. Verification in CI pending at the time of writing.

## Wasmtime INSIDE the Cosmopolitan file, wasm threads, wasm SIMD, Tint as wasm (measured 2026-10-30, Wasmtime v50.0.0, cosmocc 4.0.2)

**Wasmtime linked into the executable (workflow `wasmtime-bundle`, job `static-link`).** `libwasmtime.a` is built from source for the Rust musl target (C parts with the Cosmopolitan compiler) and linked with the host into one Cosmopolitan executable: no dlopen, no extraction.
- Needed: stubs for the Linux calls Cosmopolitan lacks (`epoll_*`, `eventfd`, `mkfifo`, `waitid`; `ci-wasm-host/static-stubs.c`); Rust's I/O reactor (mio) built with `--cfg mio_unsupported_force_poll_poll --cfg mio_unsupported_force_waker_pipe` so it uses poll(2) and a pipe instead of epoll/eventfd (the eventfd stub's ENOSYS reached Rust's error formatting and crashed - found with gdb on the CI artifact: `mio::Selector::new -> eventfd`). Cosmopolitan's own `strerror_r` already has the POSIX (XSI) form (measured: returns 0 and fills the buffer), so nothing is replaced there; two earlier attempts at "fixing" it (a redefinition, then `--wrap`) only added crashes (infinite recursion through Cosmopolitan's `strerror`).
- Result on Linux x86-64: **PASS** - the host loads the wasm guest, the guest calls the host import, the host answers, exit code 0 (run 8, commit 6d9b73e).
- The same code in the fat file (x86-64 + arm64, `static-fat`) on the other four targets (run 9, commit 9be6b72): **FAIL on all four, each for a different reason, all from one cause.** Rust's standard library and its `libc` crate are compiled for the Linux musl target, so they pass **Linux's numeric constants** (clock ids, `getrandom` flags, errno values, mmap/open flags, signal numbers) to Cosmopolitan's C library, which on every other OS expects *its own run-time constants* for that OS. Measured:
  - macOS arm64: `Timespec::now` -> `clock_gettime(1, ...)` returns EINVAL (1 is Linux's CLOCK_MONOTONIC, macOS's is 6) -> `unwrap()` panic during `wasm_engine_new`/`store_new`.
  - Windows x64: `getrandom(buf, n, flags=4)` (GRND_INSECURE, Linux number) -> `errno=87` -> panic in `std::sys::random` during `wasm_engine_new`.
  - Linux arm64: panic "strerror_r failure" while module compilation (some earlier call fails; the original error is hidden behind this one - not diagnosed, no debugger for arm64 here).
  - Even if each of those were translated, macOS arm64 would still not be able to run Wasmtime's JIT: code compiled for `*-linux-musl` does not use `MAP_JIT` / `pthread_jit_write_protect_np`, which Apple Silicon requires for executable memory; the official macOS library does.
  So "Wasmtime (JIT) statically linked into the Cosmopolitan file" works where the host really is Linux x86-64 and nowhere else without a translation layer of unknown size. What does work on all five targets today is the **bundled** form (the four official libraries stored inside the executable, extracted to a temp file at first use, `cosmo_dlopen`ed: run 9 `bundled-test`, 5/5 PASS).
- Option that makes one implementation really static on every OS: Wasmtime's **custom-platform / no_std** build (docs: "Building Wasmtime for a Custom Platform"): no Rust std, no libc crate; the embedder supplies ~20 C functions (mmap/mprotect, TLS, locks, fibers; compiled by Cosmopolitan, so with the right constants). Costs, from the same page: **no Cranelift/Winch** (modules must be precompiled to `.cwasm` for the exact Wasmtime version and CPU target, one per architecture), **no WASI**, `signals-based-traps` off (explicit bounds checks, slower), nightly Rust and a custom target. Not tried here.
- aarch64: the static link itself works (Rust std rebuilt with x28 reserved, Cosmopolitan keeps its thread pointer there).

## D3D12 backend compiled INTO the Cosmopolitan file; Metal sources compile; GPU-choice tool (measured 2026-10-30, workflow `dawn-cosmo`, run 41022592962)

Adapter on the runners is WARP (CPU), so this proves the code path, not a hardware GPU.
- How: Dawn's D3D/D3D12 translation units are compiled as "Windows" (`DAWN_COSMO_AS_WINDOWS`) against Wine's headers plus Microsoft's DirectX-Headers, everything else stays POSIX-flavoured in the same binary. Classes shared by both flavours (`SystemHandle`, `SystemEvent`, `WaitAnySystemEvent`, `DynamicLib`) choose Windows or POSIX behaviour when the program runs. ~14 Win32 functions Dawn uses are provided by `Win32Shim.cpp`.
- Three root causes found one by one (each needed its own check):
  1. **C++ exceptions are fatal:** Cosmopolitan installs a first-in-line vectored exception handler that turns any unknown SEH exception (MSVC C++ throw = 0xE06D7363, used inside D3D12/DXGI/FXC) into a process kill. `win_shield.h` puts a handler ahead of it that passes those through.
  2. **Thread stack limits:** the Windows thread block (TEB) holds the stack bounds of the thread's *Windows* stack; Cosmopolitan runs the program on its own stacks, so exception dispatch inside D3D12CreateDevice found the stack pointer outside the bounds and the process died silently (no crash report). Fix: point the TEB stack base/limit at Cosmopolitan's stack, for the main thread and every created thread (`--wrap=pthread_create`).
  3. **Struct-returning COM methods:** MSVC passes (this, result pointer, args); GCC with ms_abi passes (result pointer, this, args). `GetResourceAllocationInfo` and 29 similar virtuals returned garbage and crashed in D3D12Core. `fix_com_struct_returns.py` rewrites the 30 declarations in d3d12*.h to the MSVC order.
- Correction: an earlier "D3D12 build success" was a stale cached library (the build step passed although objects had failed). The build step now fails on any `FAILED:` line; the successes above are from clean builds.

Native with the whole host ISA (AVX2 on x64) is 2.0x (matmul) and 2.2x (n-body) faster than baseline native, i.e. 3.2x / 4.3x faster than wasm SIMD128; on arm64 NEON is already 128-bit so there is no such gap. Scalar wasm that the compiler could not vectorise is 5-6x slower than auto-vectorised native on matmul (same as native built with vectorisation off). Relaxed-SIMD FMA changed little (5-10% on arm64). **Wasmtime v50 runtime-only, no_std, STATIC inside the one Cosmopolitan file - works on all five targets** (workflow `wasmtime-nostd`, final run 41034378094, write-up `wasmtime-nostd/NOTES.md`): Rust `no_std` crate around `wasmtime =50.0.0` (`runtime`, `pulley`, `custom-virtual-memory`, `custom-native-signals`), a 70-line C platform layer built by cosmocc (mmap/mprotect/TLS/sigaction), precompiled `.cwasm` from the official CLI (`--target x86_64-/aarch64-unknown-linux-gnu`). One `.cwasm` per architecture runs on every OS. Fat file with both architectures: 1.93 MB (2.42 MB with 15 modules embedded) versus several MB per bundled official library. Speed equals the official runtime (0.98-1.06x, interleaved). Traps (out-of-bounds, divide by zero, unreachable) are caught and the instance keeps working. Costs and limits: no Cranelift (modules must be precompiled, runtime and compiler must be the same Wasmtime version/config); explicit-bounds-check mode (no signal handlers) is 0.53-0.75x on dense array loops, ~1.0x on branchy integer code; Pulley interpreter 9-165x slower (fallback only); **one wasm thread per process** until the per-thread lookup stops using x28 (Cranelift allocates x28, Cosmopolitan's thread pointer on arm64; fixed for one thread by saving/restoring x28 around wasm entry, host callbacks and the signal handler); on Windows Cosmopolitan reports the instruction address in `si_addr` so Wasmtime is told "address unknown".

## Session of 2026-10-30 (part 3): Metal in the file, Dawn Cosmopolitan vs native, why the file cannot be code-signed (measured in CI)
**Metal backend compiled INTO the Cosmopolitan file works on macOS 26 arm64** (workflow `dawn-cosmo`, run 41034054904; backend id 5, "Apple Paravirtual device", hash `9761e8ede774e783` like every other backend). A macOS job compiles Dawn's 25 Metal sources + 2 Apple-only helpers with the Cosmopolitan clang (`-mclang`, Objective-C++, no ARC) against the Apple SDK using the exact flags/definitions exported from the arm64 Dawn build (`dawn-cosmo/metal/export_inputs.py`, `build_objs.py`); the objects are linked into the arm64 half only; `objc_shim.c` (generated from the objects' undefined symbols; functions = symbols reached by CALL26/JUMP26 relocations, the rest data) resolves frameworks, classes, selectors, constant strings and the `@available` runtime check when the program starts (`dawn_cosmo_objc_init`, macOS only). Metal's command-buffer callbacks are not used (they would run on threads without Cosmopolitan's x28 thread pointer): a Cosmopolitan thread waits for each committed buffer and runs Dawn's handlers. Dawn's `Instance.cpp` reaches the backend through a weak symbol, so the x86-64 half and other OSes simply have no Metal. A policy flaw surfaced: with Metal and MoltenVK both visible the policy picked MoltenVK (larger memory figure); macOS now starts Metal only (`DAWN_COSMO_ALLOW_VULKAN=1` re-enables Vulkan for comparisons).

**Dawn compiled by Cosmopolitan vs native Dawn** (workflow `dawn-bench`, same source `dawn_bench.cpp`, interleaved rounds, a second native run as the noise floor; CI runners have no GPU, so this is the CPU side plus software/virtual adapters):
- Linux x64 (Vulkan on a software GPU; noise floor within ~5%): process total 775 ms native vs 1043 ms Cosmopolitan; Tint WGSL parse 3.4 vs 5.4 ms (160 functions); pipeline creation 3.9 vs 4.9 ms; buffer create/release 0.51 vs 0.85 us; command recording 12.4 vs 14.2 us; submit+map round trip 39.0 vs 39.5 us; adapter/device start-up equal; kernel speed equal. Cause measured in isolation (`alloc-probe`, reproduced locally): Cosmopolitan's C library takes **29-45 ns per malloc/free pair vs 7-10 ns** (glibc), **14-21 ns per uncontended mutex lock/unlock vs 4-6 ns**, and with 4 threads **~400 ns per allocation vs ~13 ns** (one global lock). Dawn allocates and locks constantly. Fix tried: a 60-line per-thread small-block cache behind `operator new/delete` (`alloc-probe/tcache_new.cpp`): 4.1 ns single-threaded and 9.2 ns on 4 threads in the probe (native 11.4 / 12.7). Linked into every fat executable from now on; its effect on Dawn is to be read from the next `dawn-bench` run. The mutex cost remains.
- macOS arm64 (Metal on a virtual M1, 5 rounds, noise floor up to ~20% and larger on start-up): Tint parse 7.5 vs 9.5 ms (0.79x), pipeline 25.4 vs 21.3 ms, buffer create equal, command recording 35.8 vs 14.8 us (**Cosmopolitan 2.4x faster, confirmed by the native repeat, cause unknown**), submit+map 1.02 vs 0.93 ms, readback 7.2 vs 7.7 GB/s; adapter request 31 vs 58 ms (framework loading and the Objective-C shim). GPU-kernel and memcpy rows on this run are invalid (the compiler removed the native memcpy; the virtual GPU's kernel timing is implausible) and are not used.
- Windows: native Dawn built with MSVC returns "no device" on the runner in this benchmark (the Cosmopolitan build gets a device); being diagnosed, so no Windows comparison yet.

**Why the Cosmopolitan file cannot be code-signed on Windows** (platform-probes): the PE header inside the file declares 2 data directories (`NumberOfRvaAndSizes = 2`, optional header 128 bytes) and a Mach-O header follows it directly; signing needs the 5th directory (certificate table). `Set-AuthenticodeSignature` says "not a valid Win32 application", `signtool` 0x800700C1, `osslsigncode` a PKCS7 decoding error. `platform-probes/pe_prepare_for_signing.py` writes a second PE header with 16 directories into zero padding (offset 0x1000) and points `e_lfanew` at it; the file still runs on Linux; whether Windows accepts and signs it is the next probe result.

**Wasm compiled to C ahead of time (wasm2c from wabt 1.0.37 + GCC -O3) vs Wasmtime's JIT** (linux x64, relative to native scalar): matmul SIMD 0.46-0.47x (Wasmtime 0.65x), scalar 0.10-0.12x (Wasmtime 0.16x), n-body 0.52-0.55x (Wasmtime 0.51x), transform 0.76x base ISA / 1.03x host ISA (Wasmtime 1.14x), sort 1.18x, hash 1.0x; bytecode-interpreter kernel 0.79x (wasm2c host-ISA build) vs 0.40x (Wasmtime, SIMD build). wasm2c does not support relaxed SIMD. So translating wasm to C does not beat the JIT in general and does not recover native auto-vectorisation; what it removes is the need for a JIT and executable memory.

## Session of 2026-10-30 (part 4): Dawn Cosmopolitan vs native with the allocator cache, what explains the remaining gaps (workflow `dawn-bench`, dawn-cosmo run 41058681354, 7 interleaved rounds, median)
CI runners have no GPU: Vulkan = llvmpipe, D3D12 = WARP, Metal = "Apple Paravirtual device". Run-to-run variation between two runs of the same workflow was up to ~10% on process totals (Linux x64: 0.96x one run, 0.89x the next), so differences below ~10% are not claims.
New variant `native-tcache` = the native benchmark with the same per-thread allocator cache as the Cosmopolitan build (`alloc-probe/tcache_new.cpp`), to separate the allocator from everything else.
| | Linux x64 | Linux arm64 | Windows arm64 | macOS arm64 (Metal) |
|---|---|---|---|---|
| process total, cosmo / native speed | 0.89x | 0.81x | 1.01x | 1.01x |
| process total, native-tcache / native | 1.04x | 1.03x | 1.03x | 1.12x |
| allocator (host_alloc), cosmo / native | 2.8x | 3.3x | 4.6x | 5.1x |
| default mutex (host_mutex), cosmo / native | **0.26x** | **0.31x** | 0.62x | 1.11x |
| command encoding (64 dispatches), cosmo / native | 1.13x | 1.30x | 0.96x | 1.50x |
| command encoding, native-tcache / native | 1.21x | 1.23x | 1.18x | 1.17x |

- **The allocator explains the command-encoding advantage of the Cosmopolitan build**: giving the native build the same cache makes native encoding 1.17-1.23x faster on all four, i.e. as fast as or faster than the Cosmopolitan build. It also explains the macOS "2.4x faster encoding, cause unknown" of part 3 (native macOS malloc: 22.8 ns per new/delete pair vs 4.5 ns).
- **The cache is worth adopting in native builds too** (3-12% of process time here), independent of Cosmopolitan.
- **What the allocator does not explain** (native-tcache is unchanged on these rows): Tint parse is 0.66-0.70x on Linux/Windows-arm64 (not on macOS); buffer create+release on Linux arm64 is exactly the mutex ratio (0.31x); mutex lock+unlock is 3-4x slower in Cosmopolitan on Linux and 1.6x on Windows arm64 (emulated).
- **Profile of the mutex** (`perf`, Linux x64, cosmo `.dbg` ELF vs native): the Cosmopolitan lock goes `pthread_mutex_lock` -> `_pthread_mutex_lock` -> `pthread_mutex_lock_impl` -> `nsync_mu_lock` (and the same for unlock), ~6.9% of samples vs 5.5% for glibc's `pthread_mutex_lock`/`unlock` in the same program. A direct call of `nsync_mu_lock/unlock` for the default process-private mutex (`alloc-probe/mutex_fast.c`, linked with `--wrap`) took the local probe from ~22 to ~18 ns per lock+unlock (x86-64 dev machine, not CI): a part, not the whole. nsync's own fast path is one compare-and-swap each way (read in libc/intrin source, 4.0.2). The default mutex has to stay nsync-compatible because `pthread_cond_wait` uses the same word (`can_use_nsync`), so it cannot be replaced by a plain futex lock. A CI variant `cosmo-mutexfast` is added to the benchmark to measure the effect on Dawn.
- **GPU kernel**: the old `gpu_alu_GFLOPs` (millions of GFLOP/s) was a bug in the benchmark: the WGSL recurrence diverged to infinity and nothing checked the result. Fixed (contracting recurrence, last workgroup read back and compared with a CPU float reference, throughput printed only if it matches). Now Linux x64 llvmpipe 9.4 vs 9.5 GFLOP/s (native vs cosmo), Linux arm64 3.53 vs 3.55, Windows arm64 WARP 5.3 vs 4.3 (emulated x86-64). On macOS no number is printed for either build: the check against the CPU reference failed on the paravirtual Metal device for native and Cosmopolitan alike (the raw check line is now printed in the workflow; reading pending).
- **Windows ARM64: the Cosmopolitan file runs its x86-64 half under Windows' x86-64 emulation** (the benchmark now prints "[the x86-64 half of the file]"; Cosmopolitan has no native Windows-arm64 half). Start-up costs show it: instance creation 1.6 ms vs 0.075 ms, adapter 59 vs 29 ms, device 16.9 vs 5.8 ms; steady state is close (encode 0.96x, readback 0.93x, total 1.01x because WARP dominates). `host_float` 8x "faster" is a compiler artefact (the x86-64 half is auto-vectorised by GCC, the MSVC arm64 build of that loop is not), not a platform result.
- Linux arm64 `host_float_GFLOPs` 0.57x is the same kind of artefact in the other direction (cosmocc's compiler vs clang); not Dawn related.

## Session of 2026-10-30 (part 6): the default mutex, what the profile says about the remaining Dawn gaps (workflows `sync-stress`, `dawn-bench` run 41066548778 = dawn-cosmo run 41064463383, `dawn-perf` run 41066552985)
**The "mutex is 3-4x slower" row was mostly a benchmark artefact.** glibc's lock skips the atomic prefix while the process has one thread; the original `host_mutex_ns` ran single-threaded. With a second thread alive (new row `host_mutex_mt_ns`, which is what Dawn always sees: Vulkan driver threads, workers) native costs 18.2 ns (x64) / 14.9 ns (arm64) against 20.8 / 17.2 ns for Cosmopolitan = 0.87x / 0.86x. macOS (Metal) has no gap at all in either form (native 10.7, Cosmopolitan 12.0 ns).
**Futex-only mutex + condition variable (`alloc-probe/fast_sync.c`)**: uncontended threaded 17.3 (x64) / 12.9 (arm64) ns = 1.05x / 1.16x of native; Dawn-level effect nil: process total 0.98x (x64) and 0.93x (arm64) vs 0.96x / 0.87x for the plain Cosmopolitan build in the same run (differences inside the ~10% run-to-run spread); buffer create+release and Tint parse are unchanged by it. Under contention it is not better than the library's nsync lock, on arm64 and Windows clearly worse: 8 threads x 200000 locks: Linux arm64 native 140-162 ms, library 57-61 ms, fast 130-167 ms; Windows x64 library 88 ms, fast 142 ms; Linux x64 native 67, library 59, fast 72; macOS native 54, library 64, fast 72. A spin before sleeping made it worse (2x slower with 8 threads on 4 cores, local x86-64), so the default is no spin. Conclusion so far: not worth adopting for speed; the library's nsync mutex is the better contended lock (it beat glibc's mutex on arm64 in this test).
**Correctness of `fast_sync.c`** (`sync_stress.cpp`; PASS = no FAIL line): Linux x64, Linux arm64, macOS and Windows x64 pass for the library's lock and the futex lock (producer/consumer, timed waits, try-lock, recursive mutexes, `call_once`, broadcast). Run after adding cancellation points and lock deadlines: local x86-64 PASS for 4 cancellation cases (blocked wait, blocked timed wait, cancel pending before the wait, cancellation disabled around the wait; the cleanup handler runs with the mutex held, as with glibc) and 4 deadline cases; the CI run of those tests on the five targets is pending (macOS native reference does not build: no `pthread_mutex_timedlock` there). Cosmopolitan 4.0.2 has no `pthread_mutex_timedlock` / `pthread_mutex_clocklock` at all (no symbol, no declaration); `fast_sync.c` provides them. On the Windows x64 runner the native MinGW reference build failed the producer/consumer check while Cosmopolitan's library and the futex lock passed. **Cause found (correction of the line before): a bug in the test, not in MinGW's threads.** The check summed 2 x 1..50000 = 2,500,050,000 in a `long`, which is 32 bits on Windows (LLP64) and overflows; Cosmopolitan uses a 64-bit `long`, which is why only the MinGW build failed. In 32-bit arithmetic the running sum (-1,794,917,296) and the expected expression (352,566,352) differ, which matches the single FAIL line. The test now uses `long long`; confirmation run pending. **Decision (owner): the library's lock stays; none of the lock variants (`fast_sync.c`, `nsync_fast.c`) is adopted.**
**The Vulkan trampoline is not the cause of slow buffer creation**: a call into the system's libc through `cosmo_dltramp` costs 1.9 ns vs 2.2 ns for a normal call (x86-64 Linux, local).
**Tint profile** (Tint-only loop, 400 shader modules, `perf` software clock, flat, share of all samples; Linux): Cosmopolitan (GCC) spends in two compute-only places far more than native: `dawn::Keccak` 9.2% (x64) / 8.7% (arm64) vs 3.8% / 3.2% native, and one out-of-line `tint::Hashmap<ast::Identifier*,...>::Add` 7.4% (x64) / **19.5% (arm64)** where native has only 1.3% / 1.9% (`HashmapBase`, inlined into its callers). The same Cosmopolitan runs show `Token::~Token` and `std::__1::__variant_detail` dispatchers (libc++ vs native libstdc++), absent from the native top list. Next: build the same Dawn with `cosmocc -mclang` (workflow `dawn-clang`) and compare.
**Still unexplained**: `buffer_create_release` is 0.74x (x64) and 0.30x (arm64) in the Cosmopolitan build and does not move with the mutex or allocator; next step is a profile of that loop on arm64.
**GPU kernel now verified on Linux**: CI check lines (`gpu_alu: groups=... last-workgroup max relative error 5.8e-08` x64 llvmpipe, `4.7e-07` arm64 llvmpipe) show the result matches the CPU reference; throughput 8.1 GFLOP/s x64 and 3.56 arm64, identical for native and Cosmopolitan (the one-round table value of 10.25 for Cosmopolitan x64 is noise on a loaded runner; the separate run printed 41.0 vs 41.1 ms). ## Session of 2026-10-30 (part 7): serving one unmodified Cosmopolitan file to Mac users (workflow `platform-distribution`; details and the owner's options in `platform-probes/SIGNING.md` section 7)
Runner: macOS 26.6 on an Apple M1 virtual machine with SIP disabled and AMFI developer mode on, so an unsigned arm64 program ran: code-signing enforcement is NOT demonstrable in CI; the tests show what the tools accept and what Launch Services does with the quarantine attribute.
- **A server can add an embedded ad-hoc signature** (`rcodesign` 0.29.0 on Linux, no Mac, no certificate; 5 ms for the universal launcher); Apple's `codesign --verify --strict` accepts it (valid on disk, satisfies its Designated Requirement), and an `.app` signed that way verifies `--deep --strict` like one signed by `codesign`.
- **It does not help against Gatekeeper.** `open -W` of unsigned, server-signed and Mac-signed bundles returned at once without the quarantine attribute and timed out with it (all three); `spctl` rejected all three. The block is the quarantine attribute, not the signature.
- **Browsers quarantine downloads and page storage.** Chrome 155 marked a downloaded file `com.apple.quarantine: 0081;...;Chrome;`; a file written by the page into its Origin Private File System carries the same attribute. A web page therefore cannot produce a quarantine-free file. File System Access dialogs and Safari were not tested.
- **The bare file starts without a compiler when a signed loader is put where the stub looks** (`${TMPDIR:-${HOME:-.}}/.ape-1.10`, no `ape` in PATH needed): `env -i PATH=/nonexistent`, loader signed by `rcodesign` or by `codesign`, bare file with and without the quarantine attribute, from `sh` and zsh: all exit 0 with the game's output and its embedded zip read. The ad-hoc signature belongs on the loader (a fixed small file), not on the game, and not per download.
- **A one-time runner app opening the file as a document works through Launch Services even when the document is quarantined** (runner ad-hoc signed, not quarantined); the same runner quarantined is blocked like the bundles. The gate moves from every game to one app. Notarization of that app (Developer ID) and the hardened-runtime exception for in-memory code were not testable.
- **Recommended structure for a store serving the unmodified file:** a notarized store client that downloads (no quarantine) and places the signed loader, or a notarized one-time runner registered for the extension; terminal one-liner for developers; a notarized `.app` per game only if neither fits. Nothing done in the browser removes the block.
